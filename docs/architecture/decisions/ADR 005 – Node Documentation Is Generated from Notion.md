# **ADR 005 – Node Documentation Is Generated from Notion**

**Status:** Accepted (documented retroactively)
**Date:** 2026-09-10
**Authors:** REDBot maintainers

---

## **Context**

RedBot ships 109 Node-RED nodes. Each one needs its help text in **three**
places:

1. **In the editor.** Node-RED renders the node's help panel from an inline
   `<script type="text/x-red" data-help-name="<nodeType>">` block inside
   `nodes/<name>.html`. It is HTML, embedded in the same file as the node's
   configuration form, and it is what a user reads while wiring a flow.
2. **On the website.** Users looking for documentation before installing, or
   linking to it from a forum answer, need a browsable page.
3. **In the repository.** Contributors and coding agents need the same text
   without a network round trip.

Keeping three copies in sync by hand does not work: the editor help is buried in
a 500-line HTML file next to the form markup, so it drifts; and the audience that
writes documentation (screenshots, examples, cross-links between nodes) is not
the audience that edits `.html` files.

The documentation is authored in **Notion**, in the
[RedBot workspace](https://redbot.notion.site/RedBot-Documentation-1de27db692114f4db163f10e1586dc71),
one page per node, because that is where the writing, the screenshots and the
review actually happen — Notion is the source the maintainers keep current.

That leaves the question this ADR settles: which of the three copies is
authoritative, and how do the other two get there.

## **Decision**

**Notion is the single source of truth for node documentation. The editor help
and the repository markdown are both build artifacts, generated by
`npm run build-docs`. Neither is edited by hand.**

```
                    ┌──────────────────────────────┐
                    │  Notion  (source of truth)   │
                    │  one page per node           │
                    └──────────────┬───────────────┘
                                   │  @notionhq/client + notion-to-md
                    ┌──────────────▼───────────────┐
                    │  bin/import-from-notion.js   │
                    │  driven by bin/nodes.js      │
                    └──────┬────────┬──────┬───────┘
                           │        │      │
       ┌───────────────────┘        │      └──────────────────┐
       ▼                            ▼                         ▼
docs/nodes/<nodeType>.md    nodes/<name>.html          docs/nodes.md
docs/assets/<hash>.png      (data-help-name block,     CHANGELOG.md
(markdown + local images)    images inlined base64)    (generated indexes)
```

### The manifest

[`bin/nodes.js`](../../../bin/nodes.js) is the list of what gets imported — one
entry per documented node:

```js
{
  notionUrl: 'https://www.notion.so/redbot/Quick-Replies-node-200e9ae1a1fd459baa29c76d6a4025e2',
  nodeFile: 'chatbot-quick-replies.html',
  nodeType: 'chatbot-quick-replies'
}
```

A node **absent from this manifest keeps whatever help is written in its
`.html`** — the importer never touches it. That is the escape hatch for a node
whose Notion page does not exist yet (see *Consequences*).

### What the importer does

[`bin/import-from-notion.js`](../../../bin/import-from-notion.js), for each
manifest entry:

1. Extracts the 32-character page id from the Notion URL and converts the page
   to markdown with `notion-to-md`.
2. **Downloads every image to `docs/assets/`**, named by an md5 of its URL, and
   rewrites the markdown to point at the local copy. This is not an
   optimization: Notion serves images from S3 links carrying **short-lived
   access tokens**, so a committed markdown file referencing them would break
   within the hour.
3. Writes `docs/nodes/<nodeType>.md` — the repository copy, with local image
   paths.
4. Renders the markdown to HTML, **inlines the images as base64 `data:` URIs**,
   and replaces the `data-help-name="<nodeType>"` block in
   `nodes/<nodeFile>` with it. Inlining is required because the Node-RED editor
   serves the help from the node's own HTML with no asset pipeline behind it.
5. Regenerates `docs/nodes.md` — the index, sorted by the page title taken from
   the markdown's first `#` heading.

It also regenerates `CHANGELOG.md` from the
[Change log](https://www.notion.so/redbot/Change-log-b46a94ab6bbc4c7d8a586cbc21af7d78)
Notion page, parsing its table into a bullet list.

### Credentials, and the no-op path

The Notion token is read from `NOTION_API_KEY`, or from an untracked
`.env-notion` file at the repository root. **Without a token the importer prints
`Missing notion token, skipping` and exits 0** — deliberately, so that
`npm run build` works for a contributor who has no Notion access. It produces a
build with stale documentation rather than no build.

### Where it runs

| Command | Effect |
| --- | --- |
| `npm run build-docs` | the importer alone |
| `npm run build` | webpack production build **then** the importer |

So a release build refreshes the documentation as a side effect, and the
generated files land in the same commit as the code.

### The consequence for contributors and agents

> **Do not edit `docs/nodes/*.md`, `docs/nodes.md`, `CHANGELOG.md`, or a
> `data-help-name` block in `nodes/*.html` for a node listed in
> `bin/nodes.js`.** The next `npm run build` overwrites the change, silently and
> completely. Edit the Notion page instead, then run `npm run build-docs`.

This is the rule most likely to be violated by someone — or something — reading
the repository and reasonably concluding the markdown is the source.

Documentation that is *not* generated, and therefore *is* edited in the
repository:

* `docs/architecture/decisions/` — these ADRs;
* `docs/best-practise.md`;
* the onboarding guides (`docs/whatsapp-onboarding.md`,
  `docs/deepchat-onboarding.md`);
* `README.md`, `CLAUDE.md`;
* every `.html` **configuration form**, and the help of any node not in the
  manifest.

### Deprecating a node

Since Notion is the source, deprecation is a Notion edit, per `CLAUDE.md`:

1. add a callout block to the node's page — question-mark icon, light grey
   background, text *"This node is deprecated"*;
2. in the documentation index page, move the link under **Deprecated nodes**.

## **Consequences**

### ✅ Positive

* One place to write, three places kept current, with no manual sync. A
  screenshot added in Notion reaches the Node-RED help panel on the next build.
* Documentation is written by whoever is best placed to write it, in a tool
  suited to it, without touching the codebase.
* The editor help is self-contained: images are base64, so it needs no asset
  server and works in an offline Node-RED.
* The repository still carries a readable, greppable copy for contributors and
  agents, and it is versioned alongside the code that it documents.
* A missing token degrades to a stale build instead of a failed one.

### ⚠️ Trade-offs / Risks

* **Generated files are committed**, so they look editable and invite exactly
  the edit that will be lost. Nothing in the tree enforces the rule — this ADR,
  `CLAUDE.md`, and the fact that the files are regenerated are the whole
  guardrail.
* **Documentation changes need Notion access.** An external contributor cannot
  fix a typo in a node's help through a pull request; the maintainers have to
  make the edit upstream.
* **The manifest is maintained by hand and drifts.** `bin/nodes.js` has 43
  entries against 109 nodes, and the drift is invisible: a node whose page was
  never added simply keeps its hand-written help forever, with nobody told. Deep
  Chat is the current example — its help lives in
  `nodes/chatbot-deepchat-receive.html` and **will be overwritten the moment a
  Notion page is added to the manifest**, so that page must be seeded from the
  existing help, not written from scratch.
* **`docs/nodes.md` is generated from page titles**, so a renamed Notion page
  silently changes the index, and duplicate titles produce duplicate rows (the
  current index shows `chatbot-rules` twice).
* **The build depends on a third-party API.** A Notion outage, a revoked token
  or a `notion-to-md` change breaks documentation generation — quietly, in the
  token case.
* **Assets accumulate.** `docs/assets/` is keyed by URL hash and never pruned:
  an image replaced in Notion leaves the old file behind.
* **Base64 inlining bloats the `.html` files**, which the editor loads in full.
* **Deletion is not propagated.** Removing a node from the manifest leaves its
  `docs/nodes/*.md` behind; only the index drops it.

## **Alternatives Considered**

| Option | Pros | Cons | Reason Not Chosen |
| --- | --- | --- | --- |
| Repository markdown as the source, published to a website | Documentation reviewed in pull requests, no external dependency, contributors can fix typos | Loses the Notion authoring experience — screenshots, drag-and-drop, comments, review — which is where the documentation is actually maintained; a static-site pipeline to build and host | The bottleneck is writing, not reviewing; Notion is what makes the writing happen |
| Editor help (`data-help-name`) as the source, extracted to markdown | Zero new tooling, help lives next to the node it documents | Help buried in a 500-line HTML file next to the form markup, which is why it drifted in the first place; images have to be base64 by hand | The problem being solved |
| Notion as the source, fetched at runtime by the editor | Always current, nothing committed | Node-RED editor would need network access and a Notion token; help unavailable offline; S3 image links expire | Unacceptable for an editor that must work air-gapped |
| Generate into `.gitignore`d files at build time only | No misleading committed artifacts | Contributors and agents lose the greppable copy; `npm install` from git would ship no help | The greppable copy is a main reason the markdown exists |
| Notion's own public share links as the documentation | Nothing to build at all | No offline help, no versioning with the code, no help panel in the editor | The editor help panel is not optional |
